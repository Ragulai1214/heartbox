# HEART BOX：NN CPU・1万試合学習 実装手順書

作成日：2026-10-29

## 1. 今回の目的と範囲

公開済みのHEART BOXに、相手の公開履歴を使って判断するNN CPUを追加する。その準備として、15ターン制で5種類のCPUを相手に強化学習を行う。

初回は**学習を行う試合を合計10,000試合、独立した学習実行は1回**とする。10万試合への自動延長や、乱数を変えた3回の学習は今回の範囲に含めない。1万試合は学習成立の確認と最初の候補モデルを得るための予算であり、強さの保証ではない。

本書は実装計画であり、作成時点でコード変更・学習・モデル公開は行わない。既存の `docs/spec.md`、`docs/requirements.md` は現在のプロトタイプの記録として残す。実装時に、変更される要件を同期する。

## 2. ユーザーが指定した要件

### ゲーム条件

- 上限を10ターンから15ターンに変更する。
- 1ターンは両者が攻撃・防御を各1回行う単位。最大30回の攻撃処理。
- 45点先取、箱の点数、破壊、リロード、同点時の到達ターン比較は維持する。
- 学習・評価・実際の対人戦で同じルールを使う。
- 学習は試合を繰り返して行い、試合終了で盤面・得点・試合内履歴をリセットする。NNの学習結果は保持する。

### 学習相手

| 番号 | 相手 | 指定された特徴 |
| --- | --- | --- |
| ① | 全履歴頻度CPU | 相手の公開済み全履歴を分析して攻撃・防御 |
| ② | ランダムCPU | 生存箱から無作為に配置・攻撃 |
| ③ | 過去のNN | 保存した以前のモデルと対戦 |
| ④ | 高得点偏重CPU | 攻撃は8・10・12点を優先。防御も高得点を優先し、必ずシールドの点数＞ハートの点数 |
| ⑤ | 最近の履歴CPU | 最近の公開履歴を分析して攻撃・防御 |

### 学習報酬

| 攻撃結果 | 攻撃した側 | 防御した側 |
| --- | ---: | ---: |
| ハート | +1 | -1 |
| シールド | -1 | +1 |
| 空箱 | 0 | 0 |

試合終了時は、勝者に+5、敗者に-5、引き分けなら双方0を追加する。最後の攻撃の報酬と勝敗報酬は両方与える。

ゲーム内得点と学習報酬は分離する。12点のハート命中でも学習報酬は+1。箱の点数による倍率や追加の報酬は導入しない。

## 3. 未指定部分に対する初期実装案

以下は上記の指定を具体化するための提案値。ユーザーが既に指定した条件と区別して設定ファイルに記載する。

| 項目 | 初期案 |
| --- | --- |
| 学習方法 | 小規模なPPO。Python・PyTorchで学習し、ブラウザは素のJavaScriptで推論 |
| NN | 共通の全結合2層、各64ユニット、tanh。行動出力25個と価値出力1個 |
| 最近の履歴 | 相手の配置・攻撃を、それぞれ直近5件使用 |
| 頻度CPUの揺らぎ | 推定価値が最大の合法手から同率なら均等選択。全体の10%は合法手から均等選択 |
| 学習相手の配分 | 最初の1,000試合は①②④⑤を各250試合、その後9,000試合は5種類を各1,800試合 |
| 過去NNの保存 | 1,000試合完了ごと。相手として使うモデルは更新を停止したコピー |
| 対戦相手の変更 | 試合開始時だけ。試合の途中では変更しない |
| 初手・プレイヤー番号 | 初手は50%。NNのA/Bも均等に割り当て、片側への依存を防ぐ |

この配分では最終的に①②④⑤は各2,050試合、③は1,800試合となる。過去の学習済みNNが存在しない初期期間を考慮した配分であり、「③に未学習モデルを混ぜて均等にした」とは扱わない。

学習用Pythonの依存ライブラリは開発環境だけに導入する。公開ゲームの「外部ライブラリなし・ビルド工程なし」は維持する。必要なパッケージと動作したバージョンは実装時に確認し、固定して記録する。

## 4. 工程1：15ターン制に統一する

1. `js/core/constants.js` の `MAX_TURNS` を15に変更する。
2. ホーム、ゲーム中、結果理由に埋め込まれた「10」を定数参照に変更する。
3. 履歴の最大件数を30件として仕様・確認項目を更新する。
4. 既存テストの最終ターン・攻撃回数を15ターン・30回へ変更する。
5. 45点到達で15ターンを待たずに終了することを維持する。
6. 同点比較がターン単位であり、同じターン内の先後では決めないことを再確認する。

**完了条件：** 両モードと画面なしの進行が15ターンに一致し、以前の10ターン表記が現行UIに残らない。過去の検証記録の日付付き数値は書き換えない。

## 5. 工程2：対戦相手の仕様を実装する

### ① 全履歴頻度CPU／⑤ 最近の履歴CPU

学習者・対戦相手のどちらにも、現在の非公開配置は渡さない。CPUごとに、自分から見た相手の記録だけを使う。

- 相手が防御した記録から、箱ごとのハート・シールド配置頻度を集計する。
- 相手が攻撃した記録から、箱ごとの攻撃頻度を集計する。
- 各箱がその記録で生存していた回数を分母にする。壊れていた箱を「選ばなかった」と数えない。
- ①は全件、⑤は各役割の直近5件から同じ集計を行う。
- 履歴0件では各生存箱を均等に扱う。少数履歴に過度に反応しないよう、均等な事前分布に相当する擬似観測1件分を加える。
- 現在の生存箱に絞り、必要な確率を再正規化する。

攻撃の候補値は「ハート命中の期待得点 − シールド命中による相手の期待得点」とする。シールド時の損失は攻撃した箱の点数ではなく、相手が置いたハートの点数。各箱にシールドがあった履歴で、そのときのハート点数を集計する。未観測なら他の生存箱の平均点を使う。

防御は合法な全配置を列挙し、次の値で比較する。

```text
配置の推定価値 = ハートの箱の点数 × (シールド箱の被攻撃確率 − ハート箱の被攻撃確率)
```

ここでの推定価値は対戦相手の行動ルールであり、NNの指定報酬を変更するものではない。

### ② ランダムCPU

既存の `CpuRandomController` を再利用する。配置は重複しない順序付き2箱を均等に選び、攻撃は生存箱から均等に選ぶ。

### ④ 高得点偏重CPU

- 攻撃：生存する8・10・12点の箱から均等選択。残っていなければ全生存箱から均等選択。
- 防御：ハートとシールドが両方高得点で、シールド＞ハートとなる合法配置から均等選択。
- 高得点箱が1個だけなら、その箱をシールドにし、残る低得点箱からハートを均等選択。
- 高得点箱が0個なら、全生存箱のうちシールド＞ハートとなる合法配置から均等選択。
- 空の候補集合、同じ箱への重複配置、大小条件の逆転を禁止する。

### ③ 過去のNN

最初の1,000試合後に学習済みモデルを保存し、1,001試合目以降から対戦相手に加える。その後は試合開始時に、それまでの1,000試合単位の保存モデルから均等に選ぶ。

相手の重みは試合中・試合間とも更新しない。相手の行動記録を学習者の行動として学習データに混ぜない。使用したモデルIDを各試合に記録する。

**完了条件：** 5種類が共通の `PlayerController` を満たし、3・4・5箱の全生存パターンで合法手を返す。固定乱数で再現できる。

## 6. 工程3：NNの入力・出力を固定する

### 入力

PythonとJavaScriptで共有する特徴量仕様を先に文書化し、順番・正規化方法・バージョンを固定する。

- 固定順の5箱（4、6、8、10、12）の生存フラグ。
- 自分と相手の得点、現在ターン、step、攻撃／防御の役割。
- 公開済み履歴から求めた、自分と相手の現在得点への到達ターン。同点時の勝敗判断に使う。
- 相手の全履歴と直近5件それぞれの、配置・攻撃の頻度、観測件数。
- 公開済みの直近5攻撃記録。攻撃者を自分／相手に変換し、当時の生存箱・配置・攻撃先・結果を固定長に符号化する。
- 履歴不足を表すマスク。存在しない記録を実在する0点記録として扱わない。

点数は45、ターンは15などの固定値で正規化する。頻度は0〜1、観測件数は最大観測数を基準にする。各定義は実装前に特徴量仕様へ明記する。

相手のCPU種別ID、内部乱数、確定前の配置、今回の判定結果、将来の履歴は入力に含めない。公開履歴の追加は攻撃結果の公開時だけとする。

### 出力と合法手

- 攻撃の5候補と、防御の順序付き2箱の20候補を固定順で定義する。
- 防御配置は `(heart, shield)` を一つの行動として選ぶ。
- 現在の役割と生存箱に応じた合法手マスクを適用し、無効な行動の確率を0にする。
- 学習中・ゲーム中とも、出力確率に従って合法手を抽選する。常に最大確率の手に固定しない。
- 価値出力は学習時に使い、ゲーム内では不要なら省略して書き出す。

**完了条件：** 同一の公開状態からPythonとJavaScriptが同じ特徴量・合法手集合を生成する。現在の非公開配置だけを変更しても入力が変わらない。

## 7. 工程4：画面なしの学習環境を作る

ゲームルールは既存JavaScriptのルール層を正とし、Pythonに別実装を作らない。

初期案は、Python学習プロセスから常駐Node.jsプロセスへJSON Linesで接続し、複数の対戦状態をまとめて進める構成とする。通信は標準入出力で行い、ログは標準エラーへ分離する。1行ごとにプロセスを再起動しない。

1. Node側でゲーム状態、5種類の相手、公開履歴を管理する。
2. NNが判断する場面で、公開情報から作った観測と合法手マスクをPythonへ渡す。
3. Pythonが返した行動をNode側で検証し、既存ルールで進める。
4. 次のNN判断場面、または試合終了までの報酬を返す。
5. 終了後の次試合には別IDを割り当てる。前試合の報酬や履歴を引き継がない。

環境は手動の「次へ」や交代画面を待たない。UIのPromise処理をそのまま学習に流用せず、ルール層を使う専用ランナーを作る。

### 報酬を渡すタイミング

防御行動の結果は相手が攻撃するまで分からない。未解決の行動を保持し、攻撃が解決した後に対応する報酬を与える。

- NNが防御した直後に相手がハートを攻撃して勝った場合：NNの最後の防御行動は `-1 -5 = -6`。
- NNの攻撃がハートに当たって勝った場合：最後の攻撃行動は `+1 +5 = +6`。
- シールドで防御側のNNが勝った場合：最後の防御行動は `+1 +5 = +6`。
- 勝敗報酬はNNの最後の遷移に1回だけ加える。過去の全行動に+5を直接繰り返し加えない。

15ターン終了は実際の勝敗が確定する終端として扱う。学習バッチの区切りは試合終端ではなく、継続中の状態として扱う。両者を混同して将来価値の扱いを変えない。

**完了条件：** 既存テストと同じ手順列で得点・盤面・勝敗が一致し、終端報酬の二重計上がない。通信異常時は不完全な試合を完了件数に数えない。

## 8. 工程5：学習器と保存・再開を作る

実装時にPPOの一次資料・使用ライブラリの仕様を確認する。以下は実験の開始値であり、性能保証値ではない。

| 設定 | 初期値案 |
| --- | --- |
| 学習率 | 0.0003 |
| 割引率 | 1.0（短い有限試合の指定報酬合計を重視） |
| GAE lambda | 0.95 |
| PPO clip | 0.2 |
| エントロピー係数 | 0.01 |
| 価値損失係数 | 0.5 |
| 勾配ノルム上限 | 0.5 |
| 更新用データ | NNの判断2,048回程度。最後のバッチは残数で処理 |
| ミニバッチ／更新回数 | 256／4 epoch |

役割・生存箱のマスク適用後の分布から行動確率、対数確率、エントロピーを計算する。学習時の確率計算と実際の行動抽選を一致させる。報酬値を自動正規化する設定は初回には入れない。

保存物には、NN重み、最適化器状態、乱数状態、完了試合数、相手配分の進捗、特徴量バージョン、ルール設定、過去NN一覧、学習設定、元コードのGitコミットを含める。保存は試合の境界を揃えた状態で行う。

並行環境を使う場合も、新規試合の割当を管理して合計10,000試合で止める。バッチ都合による無断の超過試合を避ける。

**完了条件：** 小さなテストデータで損失・勾配が有限値になり、学習の更新が起こる。中断再開で試合が重複せず、履歴・重みの取り違えがない。

## 9. 工程6：本学習前のテスト

- 15ターン30攻撃、45点途中終了、同点比較をテストする。
- 報酬の3結果×攻撃／防御と、勝ち・負け・引き分けをテストする。
- 特に、相手の攻撃で試合が終わるケースをテストする。
- ④のシールド＞ハート条件と高得点箱不足時の挙動を全生存パターンで検証する。
- ①と⑤に異なる選択傾向の履歴を与え、履歴の追加・切り捨てが選択確率に反映されることを確認する。
- 生存しなかった箱が頻度の分母に含まれないことを確認する。
- ③の相手モデルの重みが更新されないことを確認する。
- 現在の非公開配置・相手ID・未来情報の漏えいを検査する。
- PythonとJSの同一モデルについて、特徴量・logit・合法手確率が数値誤差内で一致することを確認する。目安は確率の最大絶対差1e-5以内。
- ブラウザ側にPythonや学習用ライブラリが必要になっていないことを確認する。

テスト・動作確認用の短い実行は本学習と分離し、その重みを本番の初期値として流用しない。件数も学習10,000試合とは別に記録する。

**完了条件：** 上記が成功してから初回の学習を開始する。不正手や非有限値を単に無視して学習を継続しない。

## 10. 工程7：10,000試合を学習する

1. 初期モデルを保存し、学習前評価を行う。
2. 最初の1,000試合は①②④⑤を各250試合、順序をシャッフルして対戦する。
3. 1,000試合時点のモデルを保存し、③の相手候補と固定評価相手に登録する。
4. 残り9,000試合は5種類を各1,800試合。1,000試合単位で各200試合を割り当て、順序をシャッフルする。
5. 1,000試合ごとに重みと集計を保存する。学習に使った過去NNの世代も記録する。
6. 5,000試合時点で中間評価、10,000試合時点で最終評価を行う。
7. 10,000試合で停止する。改善が乏しくても自動で追加学習や報酬変更を行わない。

記録する指標：累計試合数、NN判断回数、相手別件数・勝敗、学習報酬、ゲーム内得点差、平均終了ターン、45点到達率、攻撃／防御別の命中結果、損失、エントロピー、処理速度。

学習時間は事前に断定しない。環境を作った段階で実測し、推論・対戦・更新・評価にかかった時間から見積もる。既存のランダム5000試合テストの速度を、そのままNN学習の所要時間に使わない。

## 11. 工程8：学習効果を評価する

### 評価試合数

評価は重みを更新せず、学習とは別の乱数系列で実行する。評価でも実際のゲームと同じ確率的な行動選択を使う。

| 時点 | 相手と試合数 | 合計 |
| --- | --- | ---: |
| 学習前 | ①②④⑤に各500試合 | 2,000試合 |
| 5,000試合後 | 5種類に各500試合 | 2,500試合 |
| 10,000試合後 | 5種類に各2,000試合 | 10,000試合 |

③の評価相手は1,000試合時点のモデルに固定する。全評価でNNの先攻・後攻を半分ずつにし、各試合で相手の履歴をリセットする。

**学習10,000試合に上記の評価14,500試合は含めない。** 学習試合数を増やしているわけではない。評価量は本書の提案であり、処理速度によって削減する場合は精度への影響と変更理由を報告する。

### 比較と判断

- 相手ごとに勝ち・負け・引き分け、勝率、引き分けを0.5勝とする成績、得点差を示す。
- 勝率の95%信頼区間を出す。2,000試合・勝率50%付近の単純な概算では±2.2ポイント程度だが、実際は算出した区間を使う。
- 学習前、5,000、10,000試合の結果を並べる。学習報酬の増加だけを成功判定にしない。
- ③だけへの勝率や、平均勝率だけで採用しない。①⑤への大きな弱点を確認する。
- 最終評価用の乱数はモデル選択や設定調整に使わない。調整した場合は、新しい未使用の最終評価を用意する。

履歴を利用できているかの追加診断として、必要なら「正しい履歴」と「相手の傾向を均等に置き換えた入力」を比較する。無加工の履歴削除は学習時にない入力になる可能性があるため、診断結果だけで因果関係を断定しない。本診断の試合数は上記とは別に明記し、無断で大規模化しない。

初回の採用判断は、①②④⑤への評価で学習前より改善し、明らかな退化・情報漏えい・不正手がないことを確認して行う。何%以上なら必ず十分、という一律の基準は置かない。乱数を変えた独立学習は今回1回のみなので、学習の再現性まで確認済みとは表現しない。

## 12. 工程9：ブラウザへ統合する

1. 推論に必要な重み、特徴量バージョン、行動順、15ターン・45点の設定をJSONに出力する。
2. `CpuNnController` を追加し、既存のPromiseインターフェースを維持する。
3. 重みファイルを同じサイトから相対パスで読み込み、ゲーム開始前に準備を完了する。
4. 推論はJavaScriptの行列演算・tanh・マスク付きsoftmaxだけで実行する。外部APIへの履歴送信はしない。
5. モデルの読み込み失敗・バージョン不一致を検出する。無通知でランダムCPUへ切り替えず、再試行できるエラーを表示する。
6. 比較用のランダムCPUをコードに残す。初回評価で採用できると判断したNNをCPU対戦に接続する。性能不足なら公開中CPUを勝手に置き換えず、結果を報告する。
7. PC・スマホ幅で配置・攻撃・履歴・再試合を確認する。ローカル対戦にも15ターンが反映されていることを確認する。
8. テスト・評価・推論一致の確認後に、GitへコミットしてGitHub Pagesへ反映する。

公開するのはゲームと推論用重み。学習途中の大量ログ・最適化器状態・巨大なチェックポイントをPagesの公開元に混ぜない。保存場所と `.gitignore` を用意する。
