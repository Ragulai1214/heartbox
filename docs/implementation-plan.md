## 4. 工程2: 画面に依存しないルール層を作る

### 定数と状態

`constants.js` に箱の点数、45点、10ターン、Content、HitKind、Phaseを定義する。`gameState.js` に仕様書の初期状態を作る関数を実装する。

- 攻撃側は `step === 0 ? firstAttacker : 1 - firstAttacker`、防御側はその反対。
- 最初の攻撃側は試合開始時に一度だけ50%で決める。ターンごとには抽選しない。
- `turn` は1〜10、`step` は0または1。2回目の攻撃が終わってから次のターンに進む。
- 箱は点数で識別し、生存箱は昇順に保つ。

### 配置

`placement.js` に空の配置の生成、ボタンからの配置、移動・交換、確定可否の判定を実装する。

- ハートとシールドは各1つ、異なる生存箱に置く。
- ボタンからは空箱にだけ配置でき、同じ種類は重複配置できない。
- 置いた箱から別の箱への操作は、空なら移動、中身があれば交換。
- 配置途中の情報はGameStateに入れず、人間の入力を管理する側で保持する。
- 存在しない箱などの不正入力は、状態を変更せず拒否する。

### 攻撃の解決

`rules.js` に攻撃解決、終了条件の評価、次の攻撃への進行を分けて実装する。

| 攻撃対象 | 加点先と点数 | 盤面更新 |
| --- | --- | --- |
| ハート | 攻撃側に攻撃した箱の点数 | 攻撃した箱を破壊 |
| シールド | 防御側にハートを置いた箱の点数 | 破壊しない |
| 空箱 | 加点なし | 攻撃した箱を破壊 |

攻撃前の生存箱を保存し、公開時にTurnRecordを1件だけ追加する。履歴内の配列はコピーし、後続の状態変更で過去の盤面や得点が変わらないようにする。

### 勝敗とリロード

1. どちらかが45点以上なら即座に勝敗を確定する。
2. それ以外は10ターン目の2回目の攻撃終了後に得点を比較する。
3. 同点なら `reachedTurn` が小さい側を勝者とする。
4. 到達ターンも同じなら引き分け。双方0点も引き分け。

`reachedTurn` は加点された側だけを、その攻撃のターン番号に更新する。同じターン内の先後は比較しない。破壊で3箱から2箱になった場合だけ、次の配置までに初期5箱へ戻す。

**完了条件:** DOMやブラウザAPIを使わずに、初期状態から終了まで進行できる。

## 5. 工程3: ルールをテストする

`tests/rules.test.js` をNode.jsの組み込みテストランナーで実行する。

```powershell
node --test
```

### 必須の個別ケース

- ハート命中、シールド命中、空箱命中の加点先・点数・破壊結果。
- シールド命中の加点が、シールドの箱ではなくハートの箱の点数になること。
- 5→4、4→3ではリロードせず、3→2の破壊だけでリロードすること。
- 3箱のときシールドに当たってもリロードしないこと。
- 45点以上になったら、ターン途中でも追加攻撃せず終了すること。固定配点はすべて偶数なので、到達テストは44→48などで行う。
- 10ターン目の1回目では通常終了せず、2回目で得点比較すること。
- 同点時の到達ターン比較、同じターン内での到達による引き分け、双方0点の引き分け。
- 両方の初手プレイヤーで攻守・ターン数が正しく進むこと。
- 配置の重複拒否、移動、交換、未完成配置の確定拒否。
- 履歴の内容が実際の公開結果と一致し、後から変更されないこと。

### ランダム試合の検証

再現できる乱数を使って、ランダム同士で数千試合を実行する。試合数・45点先取の件数・10ターン終了の件数・引き分け数・平均ターン数・先攻勝率を集計する。

各試合で、攻撃回数が20以下、得点が減らない、配置時の箱数が3〜5、ハートとシールドが別箱、履歴件数が攻撃回数と一致、終了後に処理が進まないことを確認する。45点先取と10ターン終了の両方が発生することも確認する。

企画書の約70%・約30%などは参考値として扱い、完全一致を合格条件にしない。

**完了条件:** 個別テストと数千試合の検証が成功し、異常な状態や進行停止がない。

## 6. 工程4: プレイヤーと進行処理を実装する

`PlayerController` にPromiseを返す `choosePlacement(view)` と `chooseAttack(view)` を定義する。

- `CpuRandomController`: 生存箱から重複しない2箱を無作為に選んで配置し、生存箱から無作為に1箱を攻撃する。
- `HumanController`: 画面の確定操作でPromiseを解決する。
- `gameView.js`: 生存箱、得点、ターン、step、自分の役割、公開済み履歴だけを渡す。現在の配置を含めない。

CPUの公平性は、攻撃用GameViewに現在の配置が存在しないことと、渡した配列・履歴を書き換えても内部状態が壊れないことを検証する。CPUは専用の隠し状態を参照せず、渡された情報だけで判断する。

`gameFlow.js` は防御側の配置→攻撃側の選択→判定・公開→次へ待ち→終了または次の攻撃を管理する。確定済み配置は判定用に保持し、攻撃側の画面やGameViewには渡さない。

確定・攻撃・次へを連打しても、Promiseの解決、加点、履歴追加が重複しないようにする。再試合時には前の入力待ちやイベントが新しい試合に影響しないようにする。

**完了条件:** 同じルール層に対してCPUと人間の操作を差し替えられ、隠し配置が攻撃側へ漏れない。

2. `main.js` と `home.js` からモード選択で新規試合を開始する。

6. REVEALで全配置を公開し、攻撃した箱と破壊された箱を区別する。結果を1行で表示する。

箱は小さい順に横一列。次の攻撃では壊れた箱を除いて詰める。スマホでも操作ボタンと箱を選べる大きさを確保する。

## 8. 工程6: ローカル対戦と交代画面を追加する

両者にHumanControllerを使い、`handoff.js` でゲーム画面に重なる交代画面を実装する。

1. PLACE_READYで配置する側を案内し、準備OKで配置を開始する。
2. 配置確定時に箱の中身を伏せ、HANDOFFで攻撃する側への受け渡しを案内する。
3. 攻撃する側が本人確認のボタンを押したら攻撃選択を開始する。
4. 公開後に次へを押すと、次の防御側のPLACE_READYへ進む。

オーバーレイを出すだけでなく、背面の操作を無効にする。HANDOFFとATTACKの描画には現在の配置を含めない。履歴やオーバーレイを開閉しても、非公開の配置が見えないことを確認する。

**完了条件:** 端末を交代しながら2人で最後まで遊べ、受け渡し中や攻撃中に隠し配置が表示されない。

## 9. 工程7: 履歴と結果画面を完成させる

### 履歴

`history.js` に公開済み履歴だけを表示するポップアップを実装する。

- 最新を先頭に、攻撃1回につき1件、最大20件を表示。
- 当時の生存箱、ハート、シールド、攻撃位置、攻守、ターンを表示。
- 累計得点と増分を表示。加点は緑、得点なしは双方に読める色で `(+0)`。
- 配置中・攻撃選択中に開いても選択状態を保ち、閉じたら元の画面に戻る。
- 結果画面からも開けるようにし、閉じたら結果画面に戻る。

### 結果

`result.js` に勝者または引き分け、最終得点、決着理由を表示する。「もう一度」は同じモードで初期化し、最初の攻撃側も再抽選する。「ホームへ」はホームに戻す。

**完了条件:** 履歴の全表示がルール層の記録と一致する。再試合で得点・箱・履歴・選択状態がリセットされる。
